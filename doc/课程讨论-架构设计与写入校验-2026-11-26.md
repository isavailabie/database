## 0. 结论

1. **基本功能已全部实现**：F1–F5（写入、范围查询、窗口聚合、过期清理、并发访问）
   均有实现与测试，运行要求在 4 核、512 MiB、无交换空间的 Linux 容器中验收通过。
2. **老师强调的写入校验要求已满足**：
   - 同一 Series 的 timestamp 不严格递增（包括与已提交数据、与排队中批次、批内相比），
     或早于过期边界，写入都会返回错误；
   - 校验失败的批次**完全不生效**：不分配版本号、不写 WAL、不改任何内存状态，
     失败批次中合法 Series 的点同样不可见；
   - 本次新增专门验收用例 `write_validation_contract`。把校验逻辑的三处分别改坏
     做反向验证，这个用例都能发现。
3. **Benchmark 自测已就绪**：`benchmark/runner.py`（按课程口径一键评测）与
   `benchmark/compare.py`（新旧版本交替对比，每次用新库）。目前主要性能问题集中在
   **单盘 fsync**、**常驻 SST 索引随文件数增长**、**长查询尾延迟** 三处，见第 5 节。

## 1. 需求对照

| 需求 | 实现方式 | 验证 |
|---|---|---|
| F1 写入：批次原子提交、返回版本号 | 写入队列 + 单协调器组提交；一批一条 WAL 记录；全部分片应用后才推进可见版本 | 功能用例 + 180 次真实崩溃注入 |
| F1 校验：顺序 / 过期边界错误，整批不生效 | `ValidateBatch` 在入队前持锁校验，校验先于一切副作用（第 3 节） | `write_validation_contract` 等 |

| F3 窗口聚合 COUNT/SUM/MIN/MAX/AVG | 每个 `(bucket, series)` 只保存累加状态；负时间戳向下取整；COUNT 精确整型 | 功能用例 |
| F4 过期清理：单调、幂等、旧查询不受影响 | cutoff 写入 WAL 后生效；新视图使用新 cutoff；完全过期的 SST 走引用计数 GC | 功能用例、崩溃恢复用例 |
| F5 并发：多写多读、分片并行、长查询不阻塞写 | 写时复制快照；每个分片一个 apply 线程；Compaction 归并在锁外执行 | 并发压力用例、TSan 零警告 |
| 1 亿点导入 ≤ 60 分钟（同步持久化） | 组提交、增量 Flush、Size-tiered Compaction | 均匀 83.40 s / 热点 69.86 s |
| 已有 1 亿点库上 60 分钟混合读写 | 4 写 16 读，后台刷盘、合并、清理同时开启 | 零读写错误，峰值 RSS 296.20 / 299.44 MiB |

| ≥ 50 次故障注入 | 9 个阶段 × 2 种 WAL × 10 轮真实进程退出 + 50 次文件损坏 | 共 230 次，全部通过 |

## 2. 总体架构

```text
写线程 ──WriteBatch──▶ [持全局锁] ValidateBatch ──失败──▶ 返回错误（无任何副作用）
                              │ 通过
                              ▼
                       有界写入队列（背压）
                              │
                              ▼
                 写入协调器（单线程，组提交）
          分配 CommitVersion → 追加 WAL → 一次 fsync
                              │
             按 series 分片拆开，各 Shard apply 线程并行应用
                              │ 全部完成
                              ▼
                 推进 visible_version → 唤醒写者返回版本号

MemTable（每个 Shard：series_id → 递增 vector，快照共享 / 写时复制）
   │ 达到阈值
   ▼
Flush：写 SST → fsync → rename → 发布 Manifest → 轮转 WAL
   │
   ▼
Size-tiered Compaction（锁外归并） + 引用计数 GC

查询 ──▶ 准入 gate（16） ──▶ 固定 ReadView（版本 + cutoff + MemTable 快照 + SST 集合）
      ──▶ 按页索引裁剪 SST ──▶ 多路归并 ──▶ 流式 Cursor
```

### 2.1 关键设计决策

| 决策 | 理由 |
|---|---|
| **按 series_id 分片，不按时间分片** | 同一 Series 的递增校验和追加都只在一个分片内完成；时间维度靠 SST 文件、Series 区段和 128 点页的 min/max 索引裁剪 |
| **单协调器 + 组提交** | 给出全局唯一的提交顺序（版本号），多个写者共享一次 fsync；同步持久化下吞吐主要取决于 fsync 次数 |
| **一批一条 WAL 记录** | 记录完整（带校验和）才算提交；恢复只重放完整记录，天然不会出现半个批次 |
| **可见版本在全部分片应用后推进** | 跨分片批次对查询原子可见 |
| **写时复制快照的 ReadView** | 查询开始时固定视图，后续写入和过期不改变结果；长查询不持锁，不阻塞写入 |
| **增量 Flush + Size-tiered Compaction** | 写放大有界；Compaction 只在规划和发布时持锁，归并 I/O 在锁外 |
| **SST 引用计数 GC + 启动时清理孤儿文件** | 并发读取下也能回收文件，崩溃留下的未登记文件在下次打开时清除 |
| **多级背压**（队列长度、MemTable 字节、热点 Series 点数、存活 SST 数） | 把峰值 RSS 压在 512 MiB 以内；等待期间释放锁，醒来后重新校验 |

## 3. 重点：写入校验与「整批不生效」

### 3.1 规则

| 情况 | 结果 |
|---|---|
| 同一 Series，批内 timestamp 相等或回退 | 整批拒绝 |
| 同一 Series，timestamp ≤ 已提交的最后 timestamp | 整批拒绝 |
| 同一 Series，timestamp ≤ 写入队列中尚未提交批次的最大 timestamp | 整批拒绝 |
| 任一点 timestamp < cutoff | 整批拒绝（**等于 cutoff 允许**） |
| 不同 Series 之间 timestamp 无序 | 允许（要求只针对单个 Series） |
| 空批次 | 拒绝 |

`(series_id, timestamp)` 唯一确定一个点，因此重复 timestamp 一律视为违规，不做覆盖写。

### 3.2 为什么能保证整批不生效

校验发生在**所有副作用之前**，失败时只返回错误：

```text
ValidateBatch 失败 ──▶ 不入队、不分配版本、不写 WAL、
                       不更新 last_timestamps / 背压计数、不进入 MemTable
```

通过校验之后，一个批次 = 一条 WAL 记录，fsync 成功后才分发到分片，全部分片应用后才推进
可见版本。fsync 失败时整组返回错误并进入故障状态，不复用版本号。因此**查询和崩溃恢复都
不会看到半个批次**。

### 3.3 并发与重启

- **多写者写同一 Series**：校验和入队在同一次持锁中完成，并同时检查已提交状态与排队中的批次；
  协调器按队列顺序分配版本，所以被接受的写入按版本排序后 timestamp 严格递增。
- **背压等待**：写者等待时会释放锁，期间其他写入或过期可能改变状态，因此醒来后**重新校验**。
- **与过期的竞争**：`ExpireBefore` 先等写入队列清空再推进 cutoff，已排队的批次不会因此失效。
- **重启**：`last_timestamps` 由 SST 索引中每个 Series 的 `max_timestamp` 与 WAL 重放共同重建；
  cutoff 从 Manifest 和 WAL 中恢复。
- **内存**：早于 cutoff 的跟踪项在过期时裁剪，因为对应 Series 的新写入本来就必须 ≥ cutoff。

### 3.4 测试证据

`tests/tsdb_tests.cpp` 中的 `write_validation_contract`：

1. 跨批次更小、相等，批内相等、回退：全部拒绝；
2. 混合批次（3 个合法点 + 1 个违规点）：整批不可见；
3. 失败批次**不消耗版本号**（下一次成功写入的版本恰好 +1），**不推进递增跟踪**
   （失败批次里出现过的 `{2, 500}` 之后，`{2, 300}` 仍可写入）；
4. cutoff 边界：149 拒绝、150 允许；批内一个点早于 cutoff 时整批拒绝；cutoff 不能后退，重复调用幂等；
5. 重启：一部分数据已在 SST，另一部分只在 WAL（子进程写完直接 `_exit`），重启后两类来源的
   递增约束和 cutoff 依然生效，并逐点核对最终可见数据；
6. 4 个写者交错写同一 Series 共 800 次：被接受的写入按版本排序后 timestamp 严格递增，且全部可见。

反向验证（故意改坏代码后重跑全部用例）：

| 改坏的位置 | 新用例 | 原有用例中能发现的 |
|---|---|---|
| 不检查已提交的最后 timestamp | 失败 | 3 个 |
| 不检查排队中批次（并发漏判） | 失败 | **0 个** |
| 不检查 cutoff | 失败 | 1 个 |

即并发漏判这一类问题此前没有测试覆盖，现已补上。新用例在 Release / Debug / ASan+UBSan
三套构建下通过，单独重复 30 次全部通过。

## 5. 当前的性能问题（下周讨论重点）

| 问题 | 现象 / 证据 | 已做的尝试与结论 |
|---|---|---|
| **单盘同步持久化是吞吐上限** | 千万点导入中 WAL fsync 约占写入阶段 40%（约 2.5 s / 6.0 s）；Flush、Compaction 与 WAL 争用同一块盘 | 把 WAL 移到锁外：写吞吐 −20.5%，未合入。锁外 Flush：完整实现且正确，吞吐无提升（mixed −0.56%），只有导入写入 p99 降 40–49%，未合入，补丁保留 |
| **Flush 持全局锁导致写入尾延迟** | 每次 Flush 约 10 ms（千万点导入共约 98 次），期间写者等待 | 锁外 Flush 能显著降低 p99；若 WAL 放到独立磁盘（`Options::wal_dir`），可能同时带来吞吐收益，待有条件复测 |
| **常驻 SST 索引随文件数增长** | 在 1 亿点库上 60 分钟混合（期间又追加 2.2–3.0 亿点）峰值 RSS 296–299 MiB；库增长到约 4 亿点后再跑 600 s 混合，峰值 425–466 MiB，逼近 512 MiB | 已用「存活 SST 数」背压把导入峰值从 978 MiB 降到 229 MiB；索引持久化 / 压缩尚未做 |
| **长查询尾延迟** | 热点库 60 分钟内出现一次约 11.3 s 的最大扫描延迟（p99 为 16.3 ms） | 每个 (Series, SST) 查询源占用一个 fd 和 8 KiB 缓冲，16 个准入名额不限制单个游标的源数量；尚未处理 |
| **恢复时间主要花在重建索引** | Open 约 4.7 s，几乎全部用于扫描 SST 重建 SeriesIndex，WAL 只有约 130 KB | 满足 60 s 要求；持久化索引可以进一步缩短 |

已经验证有效并合入的优化（便于说明迭代过程）：协调器使用专用条件变量，mixed 写吞吐
+33%（两组 +33.45% / +32.40%）；页索引二分与提前终止，长序列尾部窄查询 +78% / +67%；
Compaction 锁外归并；查询先排队再取快照，避免大量等待者固定旧数据。

## 6. 可能被问到的问题

- **为什么不允许相同 timestamp 覆盖写？** 要求规定 `(series_id, timestamp)` 唯一且严格递增，
  覆盖写会破坏「已返回的提交不再改变」的语义，因此按违规处理。
- **一个批次里有多条 Series，只有一条违规，其他能写进去吗？** 不能，整批拒绝。这是
  「批次校验失败时整批不生效」的直接要求，测试第 2 条专门覆盖。
- **过期后某条 Series 的旧数据全没了，还能从更早的时间写吗？** 不能早于 cutoff；
  从 cutoff 及之后可以继续写，因为它一定大于该 Series 被过期掉的所有旧点。
- **校验在哪一步、会不会成为瓶颈？** 在入队前持全局锁执行，代价与批大小和排队批次数成正比，
  队列长度有上限（默认 64）。fsync 是毫秒级，校验是微秒级，不是瓶颈。
- **崩溃发生在 fsync 之后、应用到 MemTable 之前怎么办？** WAL 中已有完整记录，恢复时重放；
  调用方可能没收到成功返回，但这次提交已经持久化（与常见数据库「提交结果不确定」的语义一致）。
- **为什么选单协调器而不是每个分片独立提交？** 跨分片批次需要全局原子性和统一版本号。
  分片 WAL（`Options::sharded_wal`）已经实现，但单盘上实测慢约 15%，默认关闭。
