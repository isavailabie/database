# 第二组：写入性能测试报告（含 1 亿点三轮复跑）

> 全部在**真实磁盘**上测量（`~/bench-data`，ext4 on vhdx，`/dev/sdd`）。
> 原始输出保存在本地运行日志中（未入库）。
> 引擎侧计时来自 `EngineStats` 的 `wal_sync_ns` / `flush_ns` / `compaction_ns` / `wal_bytes_written` / `series_index_entries` / `page_index_entries`。

## 0. 口径

| 项 | 值 |
|---|---|
| 机器 | WSL2，4 vCPU，ext4 on vhdx（`/dev/sdd`） |
| 构建 | Release（`-O3 -DNDEBUG`） |
| 负载 | 单写线程，1000 点/批，10 000 条 series，时间戳严格递增 |
| 计时 | `write` = 写入循环；`drain` = 最终 Flush + 等后台合并收敛 + Close；`total` = write + drain；**吞吐 = points / total** |
| 版本 | `map` = `project2`（`std::map` MemTable）；`vec` = `perf/memtable-vector` |

> **口径修正**：本机 `/tmp` 是 **tmpfs（7.7 G 内存盘）**。早前在 `/tmp` 上的 5M 结果（1.27 M 点/s、分片 WAL 1.2×）**不能作为磁盘结论**；本报告全部在磁盘上重跑。

**复跑结论（重要）**：

- `vec` 三轮 **282.3 / 283.0 / 283.5 s**，波动 **0.4%**；
- `map` 三轮 **314.7 / 320.1 / 357.1 s**，波动 **13.5%**；第 3 轮慢是 fsync 累计从 177 s 涨到 211 s（磁盘状态），不是代码变化；
- 按中位：**vector 少用 11.6% 时间（吞吐 +13.1%）**；按最保守配对（map 最快 vs vec 最慢）仍有 **+11.0%**。

因此可以报告：**vector 版比 map 版快约 11–13%，且运行间波动小一个数量级。**

## 2. 时间去向（100M）

| 项 | 次数 | 累计耗时（map 三轮） | 说明 |
|---|---:|---:|---|
| WAL fsync | 100 000 | **176.8–211.5 s** | 写入循环的 56–59%，单次约 1.8–2.1 ms |
| Flush | 996–997 | 46.5–51.1 s | **持全局锁**，与写入串行 |
| Compaction | 132–133 | 98.0–101.0 s | 独立线程，与写入/Flush 时间重叠 |
| 最终 drain | — | 1.3–1.5 s | 只剩最后一段 MemTable |

> 这三项**不能直接相加**：Flush 在写路径上串行，Compaction 是并发后台 I/O。
> 准确表述：**WAL fsync 是当前观测到的最主要写路径瓶颈；Flush 有串行化开销；Compaction 是并发后台开销。**
> 每次 fsync 平均覆盖 **1 000 点**（100M / 100k 次），这个比例是后续 Group Commit 分析的关键。

WAL 写入量 1.221 GB（约 12.2 B/点），最终磁盘 1.50 GB。

## 4. 关键发现

### 4.1 fsync 是主要瓶颈，但别把三项耗时相加

100 000 次提交 = 100 000 次 fsync，累计 177–211 s，占写入循环 56–59%。

### 4.2 vector MemTable：+11–13%，且稳定性显著更好

三档规模增益一致（5M +10.7%、20M +12.3%、100M +11.0–13.1%）。三轮 100M 里 `vec` 波动 0.4%，`map` 波动 13.5%——**稳定性本身就是一个值得写进汇报的优点**。

### 4.3 峰值 RSS：240 MB（map）/ 182 MB（vec），README 的 42 MiB 已失效

**先给证据，再谈结论**：

- 存活 SSTable 数：map 56–80 个、vec 68 个；
- Series 索引项：map 140k–200k、vec 165k–170k（≈ 每文件 2 500 条，正好是一个分片的 series 数）；
- 页索引项：map 849k–909k、vec 877k–883k（100M / 128 ≈ 781k 页，多出来的是每文件每序列的尾页）。

按每项约 120 B（series 索引项，含 `std::map` 节点与页 vector 头）和 32 B（页项）估算，**常驻索引约 65–75 MB**，约占 RSS 的 30%。**剩余约 150 MB 尚未归因**（怀疑是 1000 次 Flush × 10 万点的分配/释放造成的堆碎片，以及每文件的元数据字符串），需要 heap profile（massif）确认后才能下结论。

因此：

- **不建议现在调小 `max_live_sstables`**（256 是上限，本次实际 56–80 个文件；调小它不解决碎片问题）；
- README 已在本轮更新：旧数字标注为“页索引/背压之前”，并写明当前 1 亿点 320 s / 240 MB / 12.3 s；
- 新增的 `obsolete_sstables`、`memtable_bytes` 字段已进基准输出，下一轮可直接读出。

### 4.4 恢复 12.3–13.1 s

对应重建 56–80 个文件的 series + 页索引、扫描 1.5 GB。相对 60 s 有 4.6× 余量。

## 5. 复现

```bash
git checkout project2              # 或 perf/memtable-vector
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j4
./build/tsdb_bench 100000000 --series 10000 --path ~/bench-data/db-100m   # 必须用磁盘，别用 /tmp
```

输出字段含：`throughput`（含 drain）、`write_throughput`、`drain_seconds`、`flush_ms`、`compaction_ms`、`wal_syncs`、`wal_sync_ms`、`wal_bytes_written`、`sstables`、`series_index_entries`、`page_index_entries`、`obsolete_sstables`、`memtable_bytes`、`rss_bytes`、`recovery_seconds`。

## 6. 局限

1. 100M 每版 3 轮，但**仍是同一台机器**；map 的第 3 轮说明磁盘状态会带来 ~10% 波动，跨机器对比要谨慎。
2. 导入是**单写线程**；“4 个写线程”属于第三组混合读写。
3. 存储是 vhdx 上的 ext4，不是裸盘，绝对吞吐低于物理 NVMe。
4. `drain` 只等后台合并自然收敛，不强制 `Compact()` 把整库压到底层；导入触发的 132 次合并已在写入循环内并发完成。
5. RSS 仍有约 150 MB 未归因（见 §4.3），需要 heap profile。
