# 性能优化与 Linux 验证（2026-11-25）

## 1. 结论

本轮保留四项有实测收益的改动：候选 Series 范围内的写入准入计账、连续 vector MemTable、流式多路 Compaction、8 KiB 查询块解码。同步 WAL、批次原子性、可见版本、过期及持久化协议不变。**WAL 锁外流水线未合入**：当前单盘混合负载下写吞吐下降约 20.5%，不以增加并发协议复杂度换取负收益。

最终组合在 Linux、4 逻辑 CPU、512 MiB 容器内存上限、禁交换空间下完成三轮 AB / BA / AB 对照。以下是中位数，不是挑选的最佳单次结果。

| 场景 | 基线 | 最终组合 | 速度/吞吐提升 | 耗时减少 | 进程峰值 RSS 变化 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1000 万点均匀导入，含 drain | 10.119 s | 7.81714 s | +29.45% | 22.75% | -4.11% |
| 1000 万点热点导入，含 drain | 9.15402 s | 7.47079 s | +22.53% | 18.39% | -43.34% |
| 300 万点单热点显式合并 | 0.824238 s | 0.179890 s | 4.58 倍 | 78.17% | -93.39% |

- 基线提交：`a2cb1e05c15711299a0b1c1e1b9b48b4d4df4cae`，即上一轮已经推送的功能修复版本。
- 容器：`tsdb-project2-linux-20261125`，Ubuntu 22.04、Linux ARM64、GCC 11.4、C++20 Release。

- 导入为单写线程、1000 点/批、10000 Series；热点场景为 8 Series 承担 50% 写入。`seconds` 包括写入和最终 Flush/后台合并收敛/Close 的 drain，不包括之后的恢复校验。

## 4. 保留的设计改动

### 4.1 写入准入：从全量热点表复制改为候选 Series 投影

以前每个 WriteBatch 复制整个 `hot_series_points`，对 10000 条活跃序列产生大量 map 节点分配。
现在仅建立候选批次涉及 Series 的计数投影；pending 队列仍全部统计预留字节，只把涉及候选 Series 的点增加到其 projected 计数。顺序校验、等待后重检、热点和内存限额语义保留。
`ValidateBatch` 的临时表改为预留容量的 unordered_map。

该项早期独立 Linux 三轮：均匀总时 12.8051 → 13.0661 s（速度 -2.00%），热点 12.2990 → 8.85981 s（速度 +38.82%、RSS +11.92%）。彼时有环境漂移，不据此宣称均匀稳定提升。保留理由是消除全表复制、热点收益明确、实现范围较小；最终以组合的完整对照为主要结论，不把多项收益简单相加。

### 4.2 vector MemTable：顺序追加与两级 COW

Series 持有有序 `vector<VersionedPoint>`：正常递增写入 push_back，恢复乱序二分定位后插入，同 timestamp 只保留最高版本。恢复仅新增 timestamp 增加逻辑点数，last_timestamp 取最大值；补齐恢复点数触发 Flush 的计账。

Shard 与 Series 的共享计数独立检查。即便写 A 已克隆 shard，未修改过的 B 仍可能被旧 view 共享，不能原地写 B。Scan 使用 lower_bound 后的索引，不保存会随扩容失效的 vector 迭代器；过期一次删除前缀，Flush 顺序遍历。

独立设计级三轮：100 万驻留点追加 0.473273 → 0.371343 s（速度 +27.45%），RSS 83,279,872 → 37,105,664 B（-55.44%）。最终组合结果见 §1，二者是不同实验，不拼接单项最佳值。

### 4.3 流式 Compaction：消除热点全量 map

每个输入一个 `SeriesReader`，复用 fd，固定 64 KiB 缓冲。Series 索引堆选择下一个序列，时间戳点堆归并各输入，跨文件和文件内重复键取最高版本，再应用 cutoff 和计划时的 merge_version。

点解码与归并临时空间为 `64 KiB × fan-in + O(fan-in)`，不再为单条热点创建全量 vector/map。
保留输出页索引、原编码及 Manifest 发布协议；截断、缺失文件和 pread 失败返回错误，不发布不完整 SST。

独立三轮 300 万单热点合并：0.831711 → 0.182262 s（4.56 倍），RSS 256,061,440 → 15,929,344 B（-93.78%）；最终组合在 512 MiB 下再次获得近似收益，是本轮最明确的系统设计成果。

### 4.4 查询块解码与资源生命周期

查询使用独立 `QueryReader`：固定 8 KiB pread 缓冲，跨缓冲 varint/double 解码，保留页索引窄范围寻址；legacy raw 初始定位后顺序读取。查询不再计算从未使用的 hash，Open 的完整 SST 校验仍保留。

EINTR 重试、正数短读继续 refill、零字节/错误明确报错，不静默当 EOF。Scan 初始化错误返回 Status；游标后续迭代错误释放资源后抛出；Aggregate 捕获后转 Status，不输出部分聚合结果。Close、EOF、异常都会清空 generator/callback 捕获，ScanLease 归还 view 引用和并发 gate。

独立三轮：900 万扫描点 0.523424 → 0.239102 s（2.19 倍）。百万点预载、15 秒 mixed 的写吞吐 +7.95%、扫描吞吐 +29.25%，写 p99 12,794.5 → 10,224.5 µs。该项收益足够才合入，最终组合测量见 §1。

### 6.2 尚未解决的边界

1. 本轮三轮 A/B 的预载为 1000 万点、mixed 为 30 秒；大规模验证与性能对照是不同实验。未完成已有 1 亿点库上的 **60 分钟持续混合**，不能宣称完成全部课程验收。
2. vector 乱序插入为 O(n)，大量逆序恢复最坏 O(n²)；正常写入接口仍要求递增，没有新增任意乱序写能力。
3. 快照共享时修改热点 Series 仍复制整条 buffer；前缀 erase 不收缩 capacity。逻辑 memtable_bytes 不代表实际分配字节，长游标和多条保留少量点的 Series 可能保留容量。
4. Compaction 输入数量 k 未设独立硬上限，64 KiB × k 缓冲和 fd 随 fan-in 增长；输出 Series/page 索引也随数据量增长。因此只称点合并临时空间有界，不称整个引擎内存 O(k) 或永远不超过 512 MiB。
5. 每 (Series, SST) 查询源占一个 fd 和 8 KiB 缓冲；16 游标 gate 不限制单游标源数，极端 fan-in 仍可能触发 fd/RSS 限制。
6. Aggregate 仍物化全部窗口桶和结果；未实现完全流式聚合或总查询内存预算。
7. 进程退出注入和静态文件损坏不等于硬件断电、内核缓存丢失或多盘硬件故障；Docker 虚拟磁盘结果不能外推全部 Linux 硬件。

## 7. 复现

在 Linux 下把基线源码和构建目录放在当前工程外的新目录，保留当前源码作为候选。以下目录必须尚不存在；不要清理或复用用户数据库。

```bash
mkdir /tmp/tsdb-baseline-source
git archive a2cb1e05c15711299a0b1c1e1b9b48b4d4df4cae | tar -x -C /tmp/tsdb-baseline-source
cmake -S /tmp/tsdb-baseline-source -B /tmp/tsdb-baseline-build -DCMAKE_BUILD_TYPE=Release
cmake --build /tmp/tsdb-baseline-build --parallel 4
cmake -S . -B /tmp/tsdb-candidate-build -DCMAKE_BUILD_TYPE=Release
cmake --build /tmp/tsdb-candidate-build --parallel 4

g++ -std=c++20 -O3 -pthread \
  -I/tmp/tsdb-baseline-source/include -I"$PWD/benchmarks" \
  "$PWD/benchmarks/design.cpp" /tmp/tsdb-baseline-build/libtsdb.a \
  -o /tmp/tsdb-baseline-build/tsdb_design_bench

stat -f -c %T /tmp
python3 benchmark/compare.py \
  --baseline /tmp/tsdb-baseline-build --candidate /tmp/tsdb-candidate-build \
  --output "$PWD/build/perf-ab-new" --data-root /tmp/tsdb-perf-ab-new \
  --points 10000000 --hot-points 3000000 --seconds 30 --repeat 3
```

先手动创建新的 `/tmp/tsdb-baseline-source` 目录。在隔离容器或 cgroup 中设置 4 CPU、512 MiB、禁交换空间；不要仅绑定引擎的后台线程而让其他线程不限核。构建可临时增加内存，正式运行前恢复限额。

```bash
ctest --test-dir /tmp/tsdb-candidate-build --output-on-failure
ctest --test-dir /tmp/tsdb-candidate-build -R '^tsdb_tests$' --repeat until-fail:10 --output-on-failure
cmake -S . -B /tmp/tsdb-asan-build -DCMAKE_BUILD_TYPE=Debug -DTSDB_SANITIZE=ON
cmake --build /tmp/tsdb-asan-build --parallel 2
ASAN_OPTIONS=detect_leaks=1:halt_on_error=1 \
UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1 \
ctest --test-dir /tmp/tsdb-asan-build --output-on-failure
```

最初误将数据库放到宿主共享输出目录的 `admission/` 实验已中止，不用于本报告的主要性能结论。`compare.py --data-root` 将日志和被测数据层分离，并对已有目录、数据库、悬空链接、无效参数、重复场景、超时、非零退出、缺失/nonfinite 指标和恢复失败做拒绝或失败记录。
