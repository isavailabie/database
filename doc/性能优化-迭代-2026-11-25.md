## 0. 收敛判据与执行方式

用户要求「一直迭代直到没有新的可以优化的地方」。工程上的可验证定义如下：

1. 候选先做代码与资源分析，区分「已确认问题」「性能假设」「测量缺口」。
2. 不确定的候选先在隔离 worktree 实现并做同口径 A/B；**主指标无显著收益、方向不稳定或带来正确性/内存回归的一律不保留**，理由写入本文。
3. 每一轮 push 前，该轮全部改动必须通过 Release、Debug、ASan+UBSan 回归，
   180 次真实进程退出 + 50 次文件损坏注入，Python 协议用例与设计烟测，
   Release 功能套件连续 10 轮，并完成性能对照；文档与原始结果一起提交。
4. 当剩余候选全部被评估，且没有新的、可重复证明收益且风险可控的改动时，
   写「收敛结论」并做最终推送。此处「没有新的可以优化的地方」指
   **没有值得保留的改动**，不等于理论上不存在更激进的重构。

平台固定：Linux ARM64 容器、GCC 11.4、C++20 Release、4 逻辑 CPU、512 MiB、
无交换空间，数据目录为容器 `/tmp` 的 overlayfs 数据层；同步持久化与
group commit 语义不变。构建阶段内存临时放宽，正式回归与测量恢复限额。

## 1. 第 1 轮：补齐验收与确定项

**基线**：`c99b8ab5336e3882e86a6251c0098f905decf71b`（上一轮已推送版本）。
**结论先行**：本轮唯一可重复证明的吞吐收益是**长序列尾部窄范围查询**，
两组独立实验分别 **+78.29%** 与 **+67.36%**；其余场景在噪声范围内持平。
另外三项是资源生命周期与并发正确性修复，不应被表述为导入提速。

### 1.1 保留的改动

| # | 改动 | 类别 | 正确性与风险边界 |
| --- | --- | --- | --- |
| 1 | `SeriesPoints::ExpireBefore` 在闲置容量 ≥4096 且超过保留点数 4 倍时重建 buffer；`ExpireBefore` 先只读探测，无 series 需要过期时跳过整个 shard，独占 shard 不再无条件复制 series map | 已确认资源问题 | 调用方仍先做两级 COW；重建使用 vector 复制构造与 swap，异常时原 buffer 不变；只在阈值触发，避免分配震荡 |
| 2 | 页索引定位改为 `lower_bound` 跳过 `max_timestamp < max(start, cutoff)` 的页，首个候选页 `min_timestamp >= end` 时提前终止 | 性能改动 | 依赖 series chunk 内点按时间递增、页 max/min 单调；legacy raw 不走页索引；`page_end` 仍取下一页 offset |
| 3 | `Scan` 先在 gate 取得名额，再获取 ReadView | 已确认资源问题 | 等待中的查询不再固定旧 memtable/索引/SST；名额由 `ScanLease` 在失败路径归还；gate 与全局锁不同时持有 |
| 4 | `Close` 置 `scan_gate_stopping` 并唤醒 `scan_cv`；等待谓词包含停止标志 | 并发正确性 | 修复 gate 占满时 Close 后等待者永不醒、调用方 join 挂住的风险；等待者返回 `Status::Error`，不产生半个快照 |

**追加的竞态修复**：最终复核时发现初版只在 `impl_->mutex` 下直接写
`scan_gate_stopping` 并 `notify_all()`，而等待谓词是在 `scan_mu` 下求值的。
两者不是同一把锁，通知可能落在「谓词返回假」与「真正进入
`condition_variable::wait`」之间而丢失，等待者永久阻塞。现改为在 `Close`
里持 `scan_mu` 再置位、随后 `notify_all()`，使状态变更与谓词求值串行化；
锁序为 `mutex → scan_mu`，不存在反向持锁路径。该修复只影响 `Close` 与
gate 的通知顺序，不参与稳态混合读写，但仍是必须随本轮一起交付的正确性修复。

第 1 项没有把 `capacity` 直接换算成 `memtable_bytes`，因此**没有改变写入背压阈值**；
它解决的是「过期后闲置分配长期滞留」，不是宣称 `memtable_bytes` 已等于实际 RSS。

## 4. 第 2 轮：查询解码与源构造候选

### 4.1 隔离实验方式

本轮把「不确定的优化项」先做成互不影响的隔离源码树，用**完全相同**的
`benchmarks/design.cpp` 与编译命令分别链接三个版本的 `libtsdb.a`：

| 树 | 内容 |
| --- | --- |
| `base` | 第 1 轮结束状态，作为本轮基线 |
| `a` | 查询解码快路径（varint / double / 堆比较器） |
| `ap` | `a` + 选择性查询在构造源之前按页索引剪枝 |
| `ab` | `ap` + 每个 SST 常驻共享只读 fd |

实验树的编译与回归在**另一台同镜像容器**上完成，绑定宿主 CPU 4–9、独立内存限额；
正式 A/B 仍回到验收容器 CPU 0–3、512 MiB、无交换空间执行，且不与验收并发。
这样既不会让编译挤爆验收容器的 512 MiB，也不会把两组测量的磁盘 I/O 混在一起。

每个变体在隔离容器里都先跑完整 CTest（68 功能用例、180 次真实崩溃、
50 次文件损坏、42 个 Python 协议用例、6 个设计烟测）。

### 4.2 已判定拒绝：SST 常驻共享 fd（`ab`）

`ab` 在隔离容器中 **当时的 67 个功能用例里有 2 个失败**，因此不进入 A/B，也不合入：

- `query_releases_descriptors`：`descriptors() == 0` 断言失败。当前实现保证
  「没有活跃查询时不持有任何 SST fd」；常驻 fd 会让每个存活 SST 一直占一个 fd，
  改变了资源不变量，也与「宽查询需要控制源数/FD」的方向相反。
- `query_truncated_read_is_error`：把 SST 改名后期望 `Scan` 以
  `open SST query` 失败；已打开的 fd 仍指向旧 inode，改名不再被发现，
  于是查询成功返回。这会让外部文件损坏/替换被静默掩盖。

即使改用「按路径惰性 + weak_ptr 的 fd 缓存」来恢复这两条不变量，也需要一把全局
锁和额外的 inode 校验，而估计收益只是省掉每个 (series, SST) 源一次 `open/close`
（验收混合负载每次扫描约十余个源，p50 约 442 µs），相对新增的状态与语义风险
不成比例。按「不增加复杂度换微小收益」的原则，**不保留**。

### 4.3 待 A/B 判定的候选

- `a`：解码快路径。`QueryReader::ReadUvarint` 在缓冲剩余 ≥10 字节时一次性解码，
  不再逐字节检查 `Refill()`；`ReadDouble` 在剩余 ≥8 字节时直接 `memcpy`；
  归并堆比较器改为显式比较，去掉 `std::tie` 元组构造。不改变任何编码或错误语义。
- `ap`：在建源前用页索引判定该 (series, SST) 是否可能命中，跳过必然空转的源，
  省掉 8 KiB 解码缓冲与一次 `open`。注意验收混合负载的查询区间是
  `[INT64_MIN, INT64_MAX)`，属于 `full_range`，不触发剪枝；`narrow` 设计场景
  只有一个 SST。因此**预期它在现有七场景上收益接近零**，若测不出来就不保留。

### 4.4 A/B 结果

**排期**：`a` 与 `ap` 的 A/B 在第 1 轮全部回归、文档与推送完成后，于验收容器
CPU 0–3、512 MiB、无交换空间下顺序执行；七场景各 3 轮 AB/BA 交替、每次新库，
`compare.py` 拒绝缺指标、恢复丢点、非零读写错误或非有限值的结果。只有主指标
出现方向一致且超过噪声带的收益、且没有内存或正确性回归的候选才会合入主树。
实测数据写入本节并随第 2 轮一起提交，本节不预先宣称收益。

### 4.5 其余候选的复核结论

| 候选 | 复核结论 |
| --- | --- |
| Flush 全程持全局锁拆分为「冻结 / 锁外落盘 / 发布」 | 100M 导入 83 s、写入 p99 约 10 ms，理论上有约 15% 空间；但 `ClearMemtableLocked()` 会清空全部内存数据、`RotateWalLocked()` 无条件删除旧 WAL 段，锁外窗口内继续写入会造成 WAL 段含未刷盘记录而被删除。需要连同 Manifest covered version 与 WAL 轮转协议一起重写，正确性风险远高于收益。当前导入已比 3600 s 上限快 43 倍，不保留 |
| 热点 Series 分块 COW | 需把 `SeriesPoints` 从连续 vector 改成块表，牵动 Expire 前缀删除、恢复二分插入、容量回收和全部 COW 回归；在 100k 点 MemTable 窗口下收益有限，不保留 |
| Aggregate 流式封桶 | 当前 `std::map<(bucket_start, series), Bucket>` 会物化全部桶；改为按窗口封桶可降内存，但结果与错误语义要求 `Aggregate()` 在返回游标前完成，无法消除结果向量。属资源改进而非验收吞吐收益，本轮不实装 |
| Compaction fan-in 上限 | `PlanCompactionLocked` 会收齐同片同层全部输入，但实测 1 亿点库仅 56 个存活 SST、每片十余个输入、每个输入一个 fd + 64 KiB，峰值 RSS 255 MiB 以内，未构成 512 MiB 压力，不保留 |
| WAL 有界流式恢复 | `ReplayWal` 整段读入内存；但每次 Flush 都轮转 WAL，实测段大小约 1 MB，恢复 11 s 主要来自全库索引扫描而非 WAL。没有可测收益，不保留 |
| 查询源数/FD 预算 | 验收混合负载 16 游标 × 约十余源，远低于 fd 上限；宽查询的 EMFILE 属健壮性问题，不是吞吐优化，不保留 |
| 低干扰统计 | `GetStats` 在全局锁内遍历索引项并递归遍历 `sst/`；验收采样间隔 30 s，60 分钟仅 120 次调用，实测不构成 p99 抖动来源，不保留 |
| 扁平/持久化索引 | 需要改 SST 文件格式与恢复协议，超出可验证收益范围，不保留 |

收敛结论将在 `a` / `ap` 的 A/B 完成后，结合本节全部候选的复核结果给出；
在此之前不宣称已收敛。
