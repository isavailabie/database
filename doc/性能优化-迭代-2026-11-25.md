## 0. 收敛判据与执行方式

用户要求「一直迭代直到没有新的可以优化的地方」。工程上的可验证定义如下：

1. 候选先做代码与资源分析，区分「已确认问题」「性能假设」「测量缺口」。
2. 不确定的候选先在隔离 worktree 实现并做同口径 A/B；**主指标无显著收益、方向不稳定或带来正确性/内存回归的一律不保留**，理由写入本文。
3. 每一轮 push 前，该轮全部改动必须通过 Release、Debug、ASan+UBSan 回归，
   180 次真实进程退出 + 50 次文件损坏注入，Python 协议用例与设计烟测，
   Release 功能套件连续 10 轮，并完成性能对照；文档与原始结果一起提交。
4. 当剩余候选全部被评估，且没有新的、可重复证明收益且风险可控的改动时，
   写「收敛结论」并做最终推送。此处「没有新的可以优化的地方」指
   **没有值得保留的改动**，不等于理论上不存在更激进的重构。

平台固定：Linux ARM64 容器、GCC 11.4、C++20 Release、4 逻辑 CPU、512 MiB、
无交换空间，数据目录为容器 `/tmp` 的 overlayfs 数据层；同步持久化与
group commit 语义不变。构建阶段内存临时放宽，正式回归与测量恢复限额。

## 1. 第 1 轮：补齐验收与确定项

**基线**：`c99b8ab5336e3882e86a6251c0098f905decf71b`（上一轮已推送版本）。
**结论先行**：本轮唯一可重复证明的吞吐收益是**长序列尾部窄范围查询**，
两组独立实验分别 **+78.29%** 与 **+67.36%**；其余场景在噪声范围内持平。
另外三项是资源生命周期与并发正确性修复，不应被表述为导入提速。

### 1.1 保留的改动

| # | 改动 | 类别 | 正确性与风险边界 |
| --- | --- | --- | --- |
| 1 | `SeriesPoints::ExpireBefore` 在闲置容量 ≥4096 且超过保留点数 4 倍时重建 buffer；`ExpireBefore` 先只读探测，无 series 需要过期时跳过整个 shard，独占 shard 不再无条件复制 series map | 已确认资源问题 | 调用方仍先做两级 COW；重建使用 vector 复制构造与 swap，异常时原 buffer 不变；只在阈值触发，避免分配震荡 |
| 2 | 页索引定位改为 `lower_bound` 跳过 `max_timestamp < max(start, cutoff)` 的页，首个候选页 `min_timestamp >= end` 时提前终止 | 性能改动 | 依赖 series chunk 内点按时间递增、页 max/min 单调；legacy raw 不走页索引；`page_end` 仍取下一页 offset |
| 3 | `Scan` 先在 gate 取得名额，再获取 ReadView | 已确认资源问题 | 等待中的查询不再固定旧 memtable/索引/SST；名额由 `ScanLease` 在失败路径归还；gate 与全局锁不同时持有 |
| 4 | `Close` 置 `scan_gate_stopping` 并唤醒 `scan_cv`；等待谓词包含停止标志 | 并发正确性 | 修复 gate 占满时 Close 后等待者永不醒、调用方 join 挂住的风险；等待者返回 `Status::Error`，不产生半个快照 |

**追加的竞态修复**：最终复核时发现初版只在 `impl_->mutex` 下直接写
`scan_gate_stopping` 并 `notify_all()`，而等待谓词是在 `scan_mu` 下求值的。
两者不是同一把锁，通知可能落在「谓词返回假」与「真正进入
`condition_variable::wait`」之间而丢失，等待者永久阻塞。现改为在 `Close`
里持 `scan_mu` 再置位、随后 `notify_all()`，使状态变更与谓词求值串行化；
锁序为 `mutex → scan_mu`，不存在反向持锁路径。该修复只影响 `Close` 与
gate 的通知顺序，不参与稳态混合读写，但仍是必须随本轮一起交付的正确性修复。

第 1 项没有把 `capacity` 直接换算成 `memtable_bytes`，因此**没有改变写入背压阈值**；
它解决的是「过期后闲置分配长期滞留」，不是宣称 `memtable_bytes` 已等于实际 RSS。

  --baseline /tmp/round1-base-build --candidate /tmp/round1-candidate-build \

## 4. 第 2 轮：查询解码与源构造候选

### 4.1 隔离实验方式

本轮把「不确定的优化项」先做成互不影响的隔离源码树，用**完全相同**的
`benchmarks/design.cpp` 与编译命令分别链接 `base` / `a` / `ap` 三个版本的
`libtsdb.a`（`ab` 只做功能回归，不进入 A/B）：

| 树 | 内容 |
| --- | --- |
| `base` | 第 1 轮结束状态，作为本轮基线 |
| `a` | 查询解码快路径（varint / double / 堆比较器） |
| `ap` | `a` + 选择性查询在构造源之前按页索引剪枝 |
| `ab` | `ap` + 每个 SST 常驻共享只读 fd |

实验树的编译与回归在**另一台同镜像容器**上完成，绑定宿主 CPU 4–9、独立内存限额；
正式 A/B 仍回到验收容器 CPU 0–3、512 MiB、无交换空间执行，且不与验收并发。
这样既不会让编译挤爆验收容器的 512 MiB，也不会把两组测量的磁盘 I/O 混在一起。

`base` / `a` / `ap` 在最终源码树（68 功能用例）上完整 CTest 5/5 通过，
包括 180 次真实崩溃、50 次文件损坏、42 个 Python 协议用例与 6 个设计烟测。
`ab` 在功能用例上即被判定失败，未进入 A/B；其结论后来又在最终 68 用例源码上
复核（见 §4.2）。隔离容器里早期快照只有 67 个功能用例，
`Testing/Temporary/LastTest.log` 中残留的 `[1/67]` 属于那次运行；
最终二进制实测为 `[68/68]`，并在最终源码上重跑过完整 CTest。

### 4.2 已判定拒绝：SST 常驻共享 fd（`ab`）

`ab` 在**最终 68 个功能用例**上复核为 **2 个失败、66 个通过**，因此不进入 A/B，
也不合入。复核方式是把 `ab` 的 `src/tsdb.cpp`（规范化换行后与最终基线只差
A / AP / B 三处补丁，且同样含 `Close()` 丢失唤醒修复）放进最终 68 用例源码树
重新编译运行（输出见 `build/performance-20261125/r2f-ab-recheck.log`）；
早期 67 用例快照上的失败集合完全相同。两个失败用例是：

- `query_releases_descriptors`：`descriptors() == 0` 断言失败。当前实现保证
  「没有活跃查询时不持有任何 SST fd」；常驻 fd 会让每个存活 SST 一直占一个 fd，
  改变了资源不变量，也与「宽查询需要控制源数/FD」的方向相反。
- `query_truncated_read_is_error`：把 SST 改名后期望 `Scan` 以
  `open SST query` 失败；已打开的 fd 仍指向旧 inode，改名不再被发现，
  于是查询成功返回。这会让外部文件损坏/替换被静默掩盖。

即使改用「按路径惰性 + weak_ptr 的 fd 缓存」来恢复这两条不变量，也需要一把全局
锁和额外的 inode 校验，而估计收益只是省掉每个 (series, SST) 源一次 `open/close`
（验收混合负载每次扫描约十余个源，p50 约 442 µs），相对新增的状态与语义风险
不成比例。按「不增加复杂度换微小收益」的原则，**不保留**。

### 4.3 参与 A/B 判定的候选

- `a`：解码快路径。`QueryReader::ReadUvarint` 在缓冲剩余 ≥10 字节时一次性解码，
  不再逐字节检查 `Refill()`；`ReadDouble` 在剩余 ≥8 字节时直接 `memcpy`；
  归并堆比较器改为显式比较，去掉 `std::tie` 元组构造。不改变任何编码或错误语义。
- `ap`：在建源前用页索引判定该 (series, SST) 是否可能命中，跳过必然空转的源，
  省掉 8 KiB 解码缓冲与一次 `open`。注意验收混合负载的查询区间是
  `[INT64_MIN, INT64_MAX)`，属于 `full_range`，不触发剪枝；`narrow` 设计场景
  只有一个 SST。因此**预期它在现有七场景上收益接近零**，若测不出来就不保留。

### 4.5 其余候选的复核结论

| 候选 | 复核结论 |
| --- | --- |
| Flush 全程持全局锁拆分为「冻结 / 锁外落盘 / 发布」 | 100M 导入 83 s、写入 p99 约 10 ms，理论上有约 15% 空间；但 `ClearMemtableLocked()` 会清空全部内存数据、`RotateWalLocked()` 无条件删除旧 WAL 段，锁外窗口内继续写入会造成 WAL 段含未刷盘记录而被删除。需要连同 Manifest covered version 与 WAL 轮转协议一起重写，正确性风险远高于收益。当前导入已比 3600 s 上限快 43 倍，不保留 |
| 热点 Series 分块 COW | 需把 `SeriesPoints` 从连续 vector 改成块表，牵动 Expire 前缀删除、恢复二分插入、容量回收和全部 COW 回归；在 100k 点 MemTable 窗口下收益有限，不保留 |
| Aggregate 流式封桶 | 当前 `std::map<(bucket_start, series), Bucket>` 会物化全部桶；改为按窗口封桶可降内存，但结果与错误语义要求 `Aggregate()` 在返回游标前完成，无法消除结果向量。属资源改进而非验收吞吐收益，本轮不实装 |
| Compaction fan-in 上限 | `PlanCompactionLocked` 会收齐同片同层全部输入，但实测 1 亿点库仅 56 个存活 SST、每片十余个输入、每个输入一个 fd + 64 KiB，峰值 RSS 255 MiB 以内，未构成 512 MiB 压力，不保留 |
| WAL 有界流式恢复 | `ReplayWal` 整段读入内存；但每次 Flush 都轮转 WAL，实测段大小约 1 MB，恢复 11 s 主要来自全库索引扫描而非 WAL。没有可测收益，不保留 |
| 查询源数/FD 预算 | 验收混合负载 16 游标 × 约十余源，远低于 fd 上限；宽查询的 EMFILE 属健壮性问题，不是吞吐优化，不保留 |
| 低干扰统计 | `GetStats` 在全局锁内遍历索引项并递归遍历 `sst/`；验收采样间隔 30 s，60 分钟仅 120 次调用，实测不构成 p99 抖动来源，不保留 |
| 扁平/持久化索引 | 需要改 SST 文件格式与恢复协议，超出可验证收益范围，不保留 |

## 5. 收敛结论

**结论：本轮迭代到此收敛，主树不再引入新的性能优化项。**

判定依据（对应 §0 的收敛判据）：

1. **确定项已全部落地并验证**（第 1 轮，提交 `648e3b7`）：Expire 闲置容量回收与

   及其丢失唤醒修复。唯一可复现的吞吐收益是长序列尾部窄查询，两组独立实验
   +78.29% / +67.36%，八轮方向一致。
2. **不确定的候选项已先实验再决定**（第 2 轮）：`a` / `ap` 两个候选在四个
   A/B 会话中共留下 134 条记录，均因「无可复现正收益」不保留；共享 fd 变体
   `ab` 在功能回归中即因改变资源与错误语义被拒绝，未进入 A/B；

   WAL 流式恢复、FD 预算、低干扰统计和持久化索引，均给出不保留的具体理由。
3. **验收口径已闭合**：4 核、512 MiB、无交换空间下 1 亿点均匀/热点导入
   83.40 / 69.86 s（限 3600 s），两个已有 1 亿点的库各连续 3600 秒混合读写
   零读写错误、峰值 RSS 296.20 / 299.44 MiB；异常退出恢复少于 12 s；
   180 次真实崩溃 + 50 次文件损坏注入、68 功能用例、42 Python 用例、6 设计烟测
   在 Release / Debug / ASan+UBSan 下全部通过。系统已比课程硬性上限快约 43 倍，
   继续投入大改写（锁外 Flush / 分块 COW / 持久化索引）的收益远小于其正确性风险。
4. **最终推送前回归已重跑**（本轮）：在正式 4 核、512 MiB、无交换空间下，
   主树 Release / Debug / ASan+UBSan 三套 CTest 各 5/5 通过，Release 功能套件
   连续 10 轮通过；隔离容器里 `base` / `a` / `ap` 三棵最终源码树完整 CTest
   5/5 通过，`ab` 在最终 68 用例上复核为 2 项失败。日志见
   `build/performance-20261125/r2f-{build,debug,asan}-ctest.log`、
   `r2f-{base,a,ap}-ctest-final.log` 与 `r2f-repeat.log`。本轮没有改动引擎代码，
   第 1 轮 post-fix 的亿点导入与 60 分钟混合验收结论继续有效。

「没有新的可以优化的地方」在此严格指**没有值得保留的改动**：不是宣称理论上
不存在更激进的架构重构，而是所有已识别候选要么收益不可复现，要么风险与复杂度
不成比例，要么超出验收可测范围。若将来更换硬件、数据量级或引入宽查询/断电测试，
应重新打开 §4.5 的候选清单，而不是沿用本报告结论。

### 6.1 问题、证据与修复

| # | 问题 | 证据 | 修复 |
| --- | --- | --- | --- |
| 1 | **孤儿 SST 永久泄漏**：被 Compaction / 过期替换的旧 SST，若当时仍被查询引用，会进入只在内存中的待删除列表；`Close()` 不做 GC，`Open()` 只清理 `.tmp`，重启后这些文件再无人回收 | 第 1 轮热点验收库磁盘上 103 个 SST，MANIFEST 只登记 55 个，48 个孤儿共 27.3 MB，恰等于验收结束时 `obsolete_sstables=48`；最小复现（持有快照 → Compact → Close → 重开）残留 3 个旧文件 | ① `Open()` 成功加载 MANIFEST 后先 `fsync` MANIFEST 与根目录，再删除 `sst/` 下扩展名为 `.sst` 且不在当前文件集合中的文件，全部用 `error_code` 版本，尽力而为；② `Close()` 在最终 Flush 成功后执行一次 GC |
| 2 | **CURRENT 存在而 MANIFEST 缺失时按空库打开**：会静默丢掉全部 SST；有了 #1 的清理，还会把它们当孤儿删除 | 代码审查；CURRENT 只在 MANIFEST 改名就位后写入，此状态只可能来自外部删除或损坏 | 返回 `Manifest missing although CURRENT exists`，拒绝打开。这是 #1 能安全删除文件的前提 |
| 3 | **`GetStats` 异常不安全且持锁做文件系统 I/O**：使用不带 `error_code` 的 `recursive_directory_iterator`，并发 Flush / Compaction / GC 删除文件时可能抛出 `filesystem_error`；遍历目录、读 `/proc/self/statm` 全程持全局锁 | 代码审查；高频采样用例中，旧版 40 轮 Flush 加 1 次 Compact 耗时 8.4–13.6 s，新版约 0.18 s | 目录遍历、`getrusage`、`statm` 移到全局锁外，改用非递归 `directory_iterator` + `increment(ec)`；失败只让该项统计偏小，不再把异常抛给调用方 |
| 4 | **写协调线程空闲轮询**：与等待 `done` / 容量的写线程共用 `write_cv`，只能靠 200 µs 超时兜底 | 空闲 5 s：CPU 133.7–138.9 ms、自愿上下文切换 13,230–13,350 次（约 2.7% 单核） | 新增 `coordinator_cv`，只在入队、停止、存储失败时通知；空闲等待改为无超时 `wait`（谓词与所有通知点都在全局 mutex 下修改，不会丢失唤醒）；2 ms 组提交等待保留超时 |
| 5 | **写入跟踪表只增不减**：`last_timestamps`、`hot_series_points` 不随过期收缩，Series 持续更替时单调增长 | 1000 个 Series 全部过期后仍保留 1000 / 1000 项 | `PruneWriteTrackingLocked()`：删除 `last < cutoff` 的时间戳项（早于 cutoff 的写入本就会被拒绝，不改变任何判定）和计数为 0 的热点项；在 `ExpireBefore` 与两条 Open 路径的恢复结束后调用 |

关于 #1 的崩溃安全：Flush / Compaction 的输出在 MANIFEST 发布前就已改名就位，
如果在两者之间崩溃，该文件会成为孤儿并在下次 Open 时被删除。它的数据仍在 WAL 中
（WAL 只在 MANIFEST 发布后轮转），所以删除不丢已确认写入；故障注入的
`sstable_after_rename`（SST 已改名就位、MANIFEST 未发布）与 `compaction_before_manifest`
阶段覆盖了这一路径，恢复后由 §6.2 的磁盘一致性检查验证。

396,278,000 点，恢复数据一致。打开耗时新 / 旧为 17.28 s / 16.81 s，
差异在单次测量噪声以内，清理本身不构成可见开销。

### 6.5 性能对照

**千万点 A/B**：基线为 `52c0114` 的 Release 构建，与候选使用同一份 `benchmarks/`
源码（`diff -rq` 确认一致）和同样的编译选项；AB / BA 交替执行，每次都用新库。

| mixed 写入 p50 (µs) | 2355 → 1433（−39.2%） | 2619 → 1747（−33.3%） | 机制见下 |

mixed 写入提升的机制：组提交阶段，协调线程要等到「队列长度 ≥ 活跃写者数」，
最多等 2 ms。旧代码这一步也等在共用的 `write_cv` 上，而写者入队时的
`notify_one` 常常唤醒另一个正在等 `done` 的写者，协调线程于是基本都要睡满 2 ms。
专用 `coordinator_cv` 让每次入队都唤醒协调线程，凑齐即提交。旁证：基线写入
p50 稳定在 2.0–2.7 ms（2 ms 超时加一次 fsync），候选降到 1.3–2.2 ms；
两组会话中每秒 WAL 同步次数从 376–481 升到 460–645，单次同步覆盖的提交数从
3.3–3.5 降到 3.1–3.2，
即分组更早关闭，但等待显著减少。扫描吞吐小幅下降、峰值 RSS 上升，与同样 4 核下
写入量多出约三分之一（更多 fsync、Flush 与 Compaction）一致。按 §0 的口径，
写吞吐收益可重复、方向一致；读侧代价在 2–3% 量级，予以保留。

### 6.6 边界

1. 第 1 轮的 3600 秒运行把热点库追加到 3.96 亿点，约为验收规模的 4 倍。在这个
   规模上两个版本的峰值 RSS 都达到 425–466 MiB，接近 512 MiB 限额，扫描最大延迟
   都在 26–29 s。这属于超出 1 亿点验收口径的伸缩边界，不是本轮改动引入的；
   原因与 §1.6 第 3 条、§4.5 的常驻索引和单游标源数一致，本轮不处理。
2. 孤儿清理只在 MANIFEST 存在时执行，只删除 `sst/` 目录第一层、扩展名为 `.sst`
   且不在当前文件集合中的文件；其他文件一律不动。删除失败不影响打开，留给下次处理。
3. 跟踪表收缩只发生在过期和重启时；没有过期的长期 Series 仍会各占一项，
   这是严格递增校验本身需要的状态。
4. `GetStats` 锁外采样的收益只在高频采样时可见；验收口径的 30 s 采样下
   不影响吞吐，因此不计入性能收益。
