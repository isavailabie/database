下面先介绍 LevelDB 的数据读写流程，再说明 TTL、统计和恢复相关的实现。
01 / 数据组织与读写流程

LevelDB 的数据组织与读写流程

LevelDB 是 LSM-tree 结构的键值数据库。新写入先追加到 WAL 并进入内存表；内存表写满后刷成 SST 文件；后台 Compaction 再合并文件、清理被覆盖或删除的旧版本。读取时，系统按序列号在这些数据源中寻找当前视图下的结果。

数据怎么读

Get 和迭代器需要在内存表、不可变内存表与 SST 中找到当前读取视图对应的版本。

系统怎么恢复

MANIFEST 指明当前有效的 SST 文件；WAL 补回尚未刷入 SST 的写入。

新增功能

记录可以按时间失效

TTL 让数据在截止时间后对读取不可见，并在条件允许时由 Compaction 物理清理。

新增功能

随时查询当前物理统计

接口返回尚未回收的内部记录数、这些记录涉及的不同键数，以及与统计对应的最新序列号。

实现范围

同时修改写入、快照和恢复流程

TTL 和统计状态需要与现有的数据记录和文件版本保持一致。

讲解提示 · 可以先用一条记录串起架构

一条写入先有 WAL 记录和内存中的版本，之后可能刷成 SST，再参与后台合并。重启时要知道哪些 SST 有效，也要重放尚未刷盘的 WAL。TTL 和统计都要经过这整条路径，下面就分别看它们如何接入。

02 / TTL 读取与回收

TTL 的读取可见性与物理回收

TTL 到期后，记录对读取操作不可见；物理删除则由后台 Compaction 完成，并需确认活跃快照和旧版本不再依赖该记录。

写入时记下截止时间

保存绝对到期时间，而不是保存一个会在重启时重新起算的时长。

读取时确定是否可见

Get、迭代器和快照按各自固定的读取时间判断记录。

过期版本挡住旧值

最新值过期后按删除语义处理，不能继续查找并返回更旧版本。

后台确认后再回收

保护活跃快照和仍需遮挡旧值的记录；CompactRange 也能重写最深层 SST。

TTL 在哪里保存

普通值不变，TTL 值带有绝对截止时间

记录类型 序列号 fixed64
到期时间 用户数据
原始内容

截止时间作为记录的一部分，随着 WAL、内存表和 SST 原样传递；刷盘、合并和重启都不会续期。

读写边界

过期、零 TTL 和时间溢出都有明确语义

  • 到达或超过截止时间后，读取返回 NotFound。
  • TTL 为 0 仍写入新版本并分配序列号，只是立即不可见。
  • 期限计算溢出时拒绝写入，不占用序列号。
  • 快照固定创建时的序列号和时间；关闭数据库时钟仍继续前进。
读取与存储的区别：一条记录过期后可以已经不可读，但在 Compaction 将它移除之前，仍计入物理记录数。
讲解提示 · 用一个键的两个版本说明

先写一个普通值，再用短 TTL 的新值覆盖。新值过期后，数据库应返回 NotFound，而不是让老值重新出现。如果在新值到期前创建快照，这个快照仍按自己的创建时间读取。

03 / 统计口径与维护

统计范围与更新时机

统计包括当前 MemTable、Immutable MemTable 和有效 SST 中尚未回收的内部记录。一个键的多个版本、删除标记及已过期但尚未回收的记录均计入统计，因此需要按数据所在位置维护计数。

Flush：从内存写成 SST

计数从 runtime 转到 SST。记录没有增减，所以总数不变。

→

Compaction：合并并清理

只有实际从新版本中移除的记录，才从总数和对应键数中扣除。

内存中的部分

写入后更新，重启时从 WAL 重算

WAL 已经保存了尚未刷盘的记录，因此不再为每条写入单独落盘统计。重启后重放 WAL，再计入恢复出的 MemTable。

SST 中的部分

检查点和文件变化一起写入 MANIFEST

MANIFEST 保存逐键统计检查点和后续增减量。SST 文件的新增、删除与对应统计变化放进同一条 VersionEdit 提交。

讲解提示 · 可以把统计理解成跟随数据搬家

写入时记录先在内存里；Flush 只是搬到 SST，不能把记录算多或算少。Compaction 真的删除旧记录时才扣数。重开时把 MANIFEST 中的 SST 统计和 WAL 恢复出的内存记录合起来，就是当前统计。

04 / 故障恢复

恢复时分别处理数据、文件版本和统计

统计属于派生信息，发现统计校验失败时可以重新扫描记录；MANIFEST 记录当前文件版本，若其记录损坏，则无法可靠确定数据库状态，打开应失败。

写入出错时

不让统计和序列号越过未完成的写入

写入流程先处理 WAL 和 MemTable，再在锁内发布序列号及统计。若 WAL 追加或同步失败，数据库拒绝后续写入，等待重新打开并按日志恢复。

MANIFEST 滚动时

写好新的 MANIFEST 后再切换 CURRENT

新 MANIFEST 先写全量文件清单和统计检查点，再写本次变更并同步；成功后才更新 CURRENT。失败时保留旧恢复点。

日志尾部异常时

保留可恢复前缀，不把坏日志继续用下去

若 WAL 尾部有残缺或校验错误，重启时不复用该日志追加新数据，避免后续有效记录被尾部垃圾遮住。

旧库和辅助数据

统计可重建，文件版本损坏时返回错误

旧格式数据库或统计校验失败时，可以扫描当前记录重建统计；可选的 STATS 缓存只用于加速，写入失败不影响正确性。若 MANIFEST 的版本记录本身损坏，恢复会失败而不是猜测文件状态。

Compaction 中的边界

回收前重新确认读取视图仍然安全

合并期间有新的快照、或者系统时钟回拨，都可能改变过期判断。安装新版本前会再次检查；若读取视图不再安全，就放弃本次输出。

恢复原则：只重建能够从权威数据推导出的统计；文件版本无法确认时，不猜测数据库状态。
讲解提示 · 选一个崩溃点说明恢复逻辑

例如，SST 已经写出来、但对应 MANIFEST 变更还没提交时，重启后不能把这份孤儿 SST 当作有效数据。系统按旧 MANIFEST 恢复旧版本，之后清理未引用文件；统计增量也没有提交，因此文件和统计仍然一致。

05 / 写入开销与优化

统计维护开销与写入路径优化

为了知道每个键还有多少条内部记录，写入时要维护一张有序统计表。对按比较器递增的新键，插入时可以利用顺序，少做一次树查找。

原有做法

插入新键前要在有序表中定位

find(key)→判断是否存在→emplace(key)

对按比较器递增的新键，先查找再插入会重复定位；这类键可以直接从 map 末尾插入。

局部优化

递增的新键从末尾插入

先用比较器检查新键是否排在当前最大键之后。若是，就用 end() 提示插入位置；否则仍通过 lower_bound 查找，以正确处理已有键和自定义比较顺序。

改动只减少不必要的定位，不改变统计结果和恢复逻辑。

系统层面的取舍：精确去重需要额外状态和写入工作。优化的目标不是牺牲准确性，而是在保持计数、序列号和恢复语义不变的前提下减少不必要的查找。
讲解提示 · 说明这组测量的范围

在 Ubuntu 22 容器里，用 100k 条、单线程、256 字节值的 perf_write 各测三次。中位吞吐由 295,040 提升到 351,544 次/秒。它说明这次局部改动在该负载下有效，不代表所有写入模式都会有相同提升。

07 / 结论与后续验证

已验证范围与后续测试

测试通过说明这些场景下行为符合预期；它不能代替长时间运行，也不能推断没有覆盖的故障路径。

已有测试支持

目前可以确认

  • TTL 的写入、读取、回收和恢复行为通过了相应测试。
  • 统计在内存与 SST 之间的转移、版本提交和重启恢复有一致性测试。
  • 在指定的单线程写入负载中，局部优化的中位吞吐提升约 19.1%。
  • 百万键重开、并发写入、重复 WAL 崩溃和一种真实磁盘空间耗尽场景均通过测试。
还需要补充验证

目前还不能下结论

  • 还没有测量统计检查点不可用时，完整重建统计需要多长时间。

  • 磁盘空间耗尽测试覆盖了 MANIFEST 滚动场景，不代表所有写满磁盘的路径。
